# P2.2.1 — Water bench database foundation
## Existing domain (reuse)
WaterAnalysisSchedule: interval/next-run planning; WaterAnalysisBatch: area, trigger and target selection; WaterAssayChannel: calibrated assay state and media; WaterAnalysisRun: measured result/unit/calibration and sample media; WaterColorCalibration, WaterCalibrationCheck, WaterTrainingSample: analytical validity and reviewed standards. WaterMeasurement: existing realtime measurements. FarmKiosk/KioskCredential: provisioned area identity. MediaAsset and existing MediaStorageLayout: approved media storage. Existing batch scheduler/assay flow is operator-assisted, not a firmware command dispatcher.

## New ingress boundary
WaterBenchStations binds a configured EITEK master and ESP32-S3 slave pair to a FarmKiosk. One active station per kiosk, unique active hardware ID per role, revocation preserves history. Role-specific unique indexes do not prevent an ID reused in the opposite role; provisioning API must enforce cross-role identity under transaction. Area follows kiosk ownership; prohibit reassigning kiosk area while station/evidence exists or explicitly archive old binding before moving (future provisioning policy). Hardware ID is not an authentication secret.
WaterBenchEvidence is a raw evidence inbox scoped to station; immutable by service contract (not a database update trigger). Stable EventId from kiosk file ID, ConnectionId from serial session, optional boot/batch/session/request/capture/analyte metadata. A duplicate station/event key must compare original SHA-256 over exact payload bytes and return the same receipt only if identical; conflict for changed bytes. Payload is bounded JSON object text (not normalized jsonb, preserving exact byte representation for hash), server must compute and verify hash. CreatedAt is server receipt, KioskReceivedAt is observation time only. Capture IDs may wrap/repeat, not globally unique. A raw frame metadata row does not establish actual exposure or chemical validity. No image binary in JSON; upload via MediaAssets in P2.2.5. No direct FK from raw evidence to calibrated result because hardware batches may exist offline without preexisting BE batch; explicit validated mapping later. No API write or auto materialization in P2.2.1.

## Integration sequence
P2.2.2 align calendar/config and prevent dual schedule dispatch; P2.2.3 bind hardware batch/session to existing domain after identity/area checks; P2.2.4 validated AI result/unit/calibration linkage; P2.2.5 scoped media ingest; P2.2.6 authenticated idempotent spool upload, receipts and retention; P2.2.7 command ACK/cleaning history; P2.2.8 role/area permissions and integration tests. Keep legacy operator-assisted flow distinct. Never treat ACK as physical completion, receipt UTC as exposure, or raw color as concentration. Existing data untouched. Migration additive, down drops only new evidence tables (destructive to new data, backup first). CI checks model and generated migration script; live database application and power-loss/hardware acceptance not performed.

## P2.2.2 Backend configuration
Farm Administrator in assigned area registers one active station per area (API serialized by area row lock), with provisioned kiosk and both hardware IDs. SQL trigger reserves active hardware IDs globally across roles; immutable station identity; kiosk area cannot change with station history. Revocation releases claims, retains evidence, is not physical STOP. Existing active legacy schedule must be disabled and pending batch/run closed first; legacy scheduler refuses active WaterBench ownership. `GET/POST /api/areas/{areaId}/water-bench/station`, `PUT .../configuration`, `POST .../station/{stationId}/revoke`. Config body expectedVersion, enabled, times HH:mm UTC+7, graceMinutes, targets (three scoped valid calibrations), sampleSource. Version 0 initially disabled. `GET /api/edge/water-bench/configuration` uses existing X-Kiosk-Key session, no caller area/station argument, returns null when no active station. Effective enabled false on invalid/expired profiles. No remote actuation. Kiosk pull/apply/ack and stale-config inhibition still need integration; do not enable unattended operation. EF snapshot updated for the two water bench entities; SQL-only claim table/triggers intentionally not mapped. Legacy manual analysis endpoints remain separate operator-assisted workflows. Existing migration tests plus new calendar and SQL generation tests; real concurrent claim and authenticated end-to-end tests remain necessary.

### Deployment guard correction
The production deployment gate previously matched the revocation trigger's scoped DELETE as destructive SQL. The guard now permits only that one line inside the exact reviewed function definition for migration 20261126100000_WaterBenchConfiguration. The actual migration and bundle are unchanged. Existing IncidentId exception and destructive statement checks remain; any additional DELETE or changed trigger is rejected. CI tests positive/negative cases and checks the generated idempotent UP SQL. This remains a conservative latest-migration text guard, not a complete SQL safety analyzer.

## P2.2.3 — firmware batch observation timeline
Use existing WaterBenchEvidence as the typed event journal, no duplicate analytical batch/result tables. Identity station + boot + firmware batch, one connection and contiguous event sequence 1..512. Kiosk credential authorizes its active station, station row lock serializes ingest. POST /api/edge/water-bench/batch-events with stable event UUID, typed canonical payload and receipt; exact typed duplicate idempotent, changed UUID content or sequence rejected. Kiosk receipt is not exposure time; reaction start uses uint32 master uptime and durations 300000/120000/600000 ms. Start, session, reaction, image request, status masks, interruption are observation only. GET /api/areas/{areaId}/water-bench/batches and /{stationId}/{bootId}/{batchId} enforce area scope including historical revoked stations. No WaterAnalysisBatch/Run/Channel materialization or concentration writes: validated mapping to existing analytical records is deferred until calibration/media/result integration. Kiosk structured batch spool and eventual ordered uploader (P2.2.6) use the same contract. Other raw evidence must not share these typed batch correlation keys/kinds until a discriminator is added. Terminal status from firmware is not physical cleaning or chemical validity. No dispatch, automatic replay or recovery clearance. Current list provides start metadata; detail provides projection. Tests target transition and identity rules; HTTP/DB concurrency and real hardware tests remain.

## P2.2.4 — result assessment (quarantined)
GET .../water-bench/batches/{stationId}/{bootId}/{batchId}/results, POST .../results/{analyte}/assessment (assigned Farm Administrator). Immutable assessment per session; request UUID + canonical hash for retries. `needs_retest` records reason without concentration; `estimate_review_required` calls the existing signed-calibration WaterAiClient only after terminal firmware observations and a server-written `jpeg` receipt matching connection, session, capture and media hash. Media receipt contract {mediaId,sha256,contract:"water-bench-media-v1"}; private device media notes exact server marker water-bench:{station:N}:{boot}:{batch}:{analyte}:{capture}. P2.2.5 must implement receipt and reserve media against legacy reuse, not allow clients to assert a receipt. This stage has no receipt writer, so estimate is blocked until that stage. Operator attests actual timing, salinity, lot, source (not verified physical measurement); valid compatible calibration, unit, scope and bytes checked. Holdout error is not confidence. NH3/NH4/TAN-N remain distinct; no conversion or pH/temp substitution, sample evidence correlation follows after ingest. Assessment not inserted into WaterAnalysisRuns or WaterMeasurements and cannot publish; later explicitly validated mapping must use existing WaterAnalysisRuns, not a second production result. Legacy Analyze blocks water-bench media marker. No auto retries or physical actions. Additive migration, snapshot, unit tests; real DB concurrency/media/AI and physical validation pending.
